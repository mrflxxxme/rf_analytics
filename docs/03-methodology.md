# 03. Методология

Цель: каждая цифра на экране либо **измерена**, либо **откалибрована и проверена
вне выборки**, либо явно помечена как **оценка**. Методология версионируется
(`methodology_version` в манифесте snapshot). Любое изменение формулы — новая
версия и новый бэктест.

## 1. Единицы

- **Территория** `r`: 89 субъектов; на пилоте также города от 100 тыс. жителей.
- **Потребность** `n`: категория из `config/taxonomy.yaml` (~50 в MVP, D24).
- **Время** `t`: месяц.
- **Наблюдение**: пара `(r, n)` на дату `t`.

### Таксономия

```yaml
# config/taxonomy.yaml (схема)
- id: kids_leisure
  name: Детский досуг и развитие
  okved: ["85.41", "93.29", "88.91"]       # набор кодов, не один код
  osm_tags: ["amenity=kindergarten", "leisure=playground"]   # второй замер предложения
  search_keys: ["детский центр", "кружки для детей", …]       # контур D16
  spend_categories: ["sber:education_kids"]                   # если есть в СберИндексе
  franchise_examples: […]                                     # для D24, справочно
  min_entities_rf: 2000                                       # порог «хватает событий для бэктеста»
```

Таксономию собирают агенты, автор утверждает. Маппинг на ОКВЭД проверяется
на перекрытие: один код может входить в несколько потребностей только с явным
весом доли.

## 2. Целевая переменная (D15)

Для пары `(r, n)` и горизонта `h = 12` мес. считаем:

- **Y1 — чистый прирост:** `Δlog(active[r,n]) за t→t+h`, где `active` — число
  активных субъектов МСП с основным ОКВЭД из набора `n`.
- **Y2 — выживаемость:** доля субъектов, вошедших в реестр в окне `[t, t+3)`,
  которые остаются активными через 12 мес. после входа.
- **Реализовавшаяся потребность** (бинарная цель): `Y1` выше медианы `n` по РФ
  **и** `Y2` не ниже медианы `n` по РФ. Так отделяется реальная ниша от моды
  на открытия, где все массово открываются и закрываются.

Вторичная цель там, где доступна: рост трат по категории (СберИндекс), `h = 12`.

## 3. Признаки по слоям

Все признаки рассчитываются **только по данным, доступным на дату `t`**, с учётом
публикационного лага источника (запрещена утечка будущего, см. п. 6).

| Слой | Признак | Смысл |
|---|---|---|
| Предложение | `gap[r,n]` — остаток кросс-секционной модели плотности | Насколько предложения меньше, чем у сопоставимых регионов |
| Предложение | Динамика плотности за 12 мес. | Рынок уже насыщается или нет |
| Спрос | Рост трат по категории (если есть) | Деньги идут в нишу |
| Деньги | Реальный рост доходов, зарплат (hh, ЕМИСС), вкладов | Платёжеспособность |
| Структура | Чистая миграция, возрастные доли, урбанизация | Кто живёт и кто приезжает |
| Связи | Сигнал лидера: рост `n` в регионах-лидерах с найденным опережением (п. 7) | «Что выросло там, скоро придёт сюда» |
| Контекст | Сумма подтверждённых драйверов с затуханием по времени и расстоянию (п. 8) | События, которых ещё нет в статистике |
| Поиск | Индекс Вордстата | **Только отдельный контур**, в скор не входит до прохождения бэктеста (D16) |

### Разрыв предложения (ключевой признак)

Для каждой потребности `n` строим кросс-секционную регрессию по регионам:

```
log(density[r,n]) = β0 + β1·log(income_pc[r]) + β2·urban_share[r]
                  + β3·age_structure[r] + β4·log(pop[r]) + ε[r,n]
```

`gap[r,n] = −ε̂[r,n]`, то есть недостаток предложения относительно того, что
«положено» региону с такими характеристиками. Оценка устойчивая (Huber), со
стандартными ошибками. В досье показывается, с какими регионами идёт сравнение.

## 4. Индекс и калибровка (D5)

1. **Нормировка:** каждый признак — робастный z-score внутри потребности `n`
   по регионам (медиана/MAD), отсечка ±3.
2. **Индекс v0 (до калибровки):** равные веса по слоям (не экспертные), внутри
   слоя — равные веса признаков. Публикуется с меткой «не откалиброван».
3. **Калибровка v1:** логистическая регрессия с L2-регуляризацией на бинарную
   цель из п. 2 с **ограничением знаков** (ожидаемое направление влияния
   задаётся заранее и фиксируется в `config/model.yaml`). Признак, у которого
   знак разворачивается, исключается и попадает в отчёт. Модель остаётся
   линейной, поэтому раскладка скора по факторам точная.
4. **Скор** = откалиброванная вероятность (Platt/isotonic на валидации),
   показывается как 0–100.
5. ML-модели (градиентный бустинг) используются только как **контрольная
   планка**: если бустинг заметно точнее линейной модели, значит упущено
   нелинейное взаимодействие, и его нужно явно добавить признаком.

## 5. Уверенность

Уверенность — отдельная от скора величина, `высокая / средняя / низкая`, с
перечнем причин:

- покрытие данных пары (доля доступных признаков, свежесть);
- размер базы (число субъектов в `(r, n)`; меньше порога — низкая);
- точность бэктеста именно для потребности `n` (precision@top по `n`);
- согласие слоёв (знаки вкладов совпадают или противоречат друг другу).

## 6. Бэктест (D11)

- **Схема rolling-origin:** обучение на `t ≤ T`, проверка на исходе `T + 12`;
  `T` сдвигается помесячно в диапазоне 2018–2025.
- **Защита от утечки:** таблица `publication_lags` для каждого источника;
  признак на дату `t` берётся из версии, опубликованной до `t`.
- **Структурные разрывы:** 2020, 2022, 2024 отчитываются отдельными периодами;
  модель с дамми периодов против модели без них.
- **Базовые линии:** B0 — «рост прошлого года продолжится»; B1 — национальный
  тренд категории; B2 — случайное ранжирование.
- **Метрики:** precision@top-20% (главная, D11), Spearman ρ между скором и Y1,
  Brier score и кривая калибровки вероятностей, всё отдельно по потребностям.
- **Гейт точности:** precision@top-20% модели минус precision@top-20% B0 ≥ 15 п.п.
  в среднем по периодам проверки; результат публикуется в `/api/meta` и на плашке беты.
- **Артефакт:** `backtest_report.html` в каждом snapshot (графики по периодам,
  потребностям, вклад признаков, исключённые признаки и причины).

## 7. Волны трендов: опережение между регионами (D21)

Задача: найти пары «регион-лидер → регион-последователь» по потребности `n`.

1. Ряды `growth[r,n,t]` очищаются от тренда и сезонности (STL), берутся первые разности.
2. Для пар регионов (ограничение: оба с достаточной базой) — кросс-корреляция
   на лагах 1–12 мес.; кандидат — максимум на лаге `k > 0`.
3. **Значимость:** блочный бутстреп, затем поправка на множественные проверки
   Benjamini–Hochberg (FDR 5%): пар 89×88 на каждую потребность, ложные
   совпадения неизбежны без поправки.
4. **Проверка вне выборки:** связь, найденная на 2017–2022, должна улучшать
   прогноз последователя на 2023–2025 (Granger-тест + прирост precision).
   На карту попадают только связи, прошедшие оба фильтра.
5. На карте: дуга от лидера к последователю, длительность анимации пропорциональна
   лагу `k`, толщина — силе связи.

## 8. Драйверы и радиус влияния (D6, D21)

- Драйвер из реестра: `{тип, место (точка), дата, масштаб, затронутые потребности
  со знаком, срок наступления, источник, статус подтверждения}`.
- Влияние на пару `(r, n)`: `impact = масштаб × вес_типа × exp(−d/λ) × f(Δt)`,
  где `d` — расстояние до центра региона или города, `λ` и `f` (нарастание и
  затухание во времени) задаются явно в `config/drivers.yaml`.
- Это **модель, а не измерение**: на карте пунктир и подпись «оценка». В скор
  входит только после того, как бэктест на исторических драйверах (разметка
  событий 2019–2024 по пилотным регионам) покажет прирост качества.
  До этого — слой контекста в досье.

## 9. Миграционные потоки

Измеренные данные Росстата (прибывшие и выбывшие по направлениям). На карте —
дуги, толщина = объём, цвет = сальдо. В признаки входит чистая миграция и её
структура; сами потоки служат контекстом для объяснения.

## 10. Что публикуется вместе со скором

Для каждой пары: скор, уверенность и её причины, раскладка вкладов по слоям,
сравнительная группа для `gap`, ряды фактов, драйверы, связи, источники и даты,
snapshot и версия методологии.

## 11. Витрины измеренных фактов по реестру МСП (v0)

Это измерения, а не прогноз: они описывают прошлое и идут в индексируемый слой
(D27). Код — `etl/src/rf_etl/rsmp/marts.py`, источник — снимки реестра на 10-е
число (D34). Регион — `region_id` (D35), потребность — по **основному**
заявительному ОКВЭД субъекта и префиксам из `config/taxonomy.yaml`;
`need_id = _all` — все субъекты региона.

- **`msp_active`** — число субъектов МСП в снимке по `(дата, регион, потребность)`.
- **`msp_growth_12m`** — `ln(active_t / active_{t−12})` для снимков с шагом
  12 мес. Обе даты — один и тот же месяц, поэтому ежегодный пересмотр реестра
  10 августа входит в обе точки одинаково.
- **`msp_survival_12m`** — когорта: субъекты с признаком «вновь созданный»,
  вошедшие в реестр за 3 мес. до снимка `t` (`t−3мес < ДатаВклМСП ≤ t`); доля
  тех, чей ИНН есть в снимке `t+12`. Переезд в другой регион считается выживанием,
  регион берётся на дату входа. Субъекты, попавшие в реестр при пересмотре
  10 августа без признака «вновь созданный», в когорту не входят.
- Исключение из реестра = ИНН пропал из следующего снимка; закрытие и потерю
  статуса МСП данные не различают (шум, см. `02-data-sources.md`).
- Первая версия считается по ежегодным октябрьским снимкам; помесячный шаг —
  после T1.4.
- Дата снимка берётся из имени файла: у части документов `ДатаСост` старше
  (запись не менялась), но субъект в снимке есть.
- Снимок 2016 года почти целиком в ОКВЭД-2001. Таксономия задана в ОКВЭД2, поэтому
  строки с `ВерсОКВЭД ≠ 2014` идут только в `_all`, а потребности считаются с 2017 года.
- Коды упразднённых субъектов (80, 81, 82, 84, 85, 88 — объединения 2005–2008)
  в старых снимках переводятся в нынешний субъект; `00` (регион не указан)
  в региональные витрины не попадает, его объём — в `unknown_regions` отчёта.

ИНН используется только для сопоставления между снимками и в витрины не попадает;
ФИО и наименования не извлекаются.
